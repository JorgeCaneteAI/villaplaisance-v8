# Audit SEO — Villa Plaisance V8

**Date** : 2026-05-05
**Périmètre** : audit complet du site `v2.villaplaisance.fr` (déploiement
de `villaplaisance-v8`) — symptômes en live + causes racines dans le code.
**Méthode** :
- Côté live : `curl` (HTML brut, headers HTTP), sitemap, robots.txt, et
  4 versions linguistiques (FR/EN/ES/DE).
- Côté code : lecture de `app/Services/SeoService.php`, `LangService.php`,
  `Views/layouts/front.php`, `Views/seo/{sitemap,robots}.php`, `slugs.php`,
  `config.php`, `HomeController.php`.
**Outils non utilisés** (à passer après corrections) : Search Console,
Lighthouse, Rich Results Test, PageSpeed Insights.

---

## TL;DR — Santé : rouge

Bonne base éditoriale (~50 URLs, JSON-LD présent, structure H1/H2 propre)
et **architecture SEO côté code propre** (`SeoService` centralisé,
canonical conditionnel preprod/prod, sitemap dynamique, GA4 en consent
gate). Mais 6 problèmes critiques cassent l'indexation et le multilingue.
La majorité des fixes sont localisés (1 ligne à 30 minutes).

**Top 6 prioritaires** (ordre d'attaque) :
1. Subdomain `v2.` exposé et indexable (cause : layout sans `<meta robots>`)
2. JSON-LD `AggregateRating` invalide `5.9/5` (cause : pas de clamp + tel placeholder)
3. Multilingue cassé : `/de/` sert FR, hreflang absent du HEAD, **slugs.php mappé à l'envers**
4. `Cache-Control: no-store` sur HTML public (cause : `session_start()` global dans `config.php`)
5. URLs `v2.` qui fuient dans OG/JSON-LD (cause : `APP_URL` utilisé au lieu d'un base prod)
6. Sitemap mono-langue + trailing slash incohérent

## 🔴 Critiques

### C1. Subdomain `v2.villaplaisance.fr` 100% indexable

**Symptôme live** :
- `https://v2.villaplaisance.fr/` retourne 200
- `<head>` ne contient aucune `<meta name="robots">` (vérifié, 0 occurrence)
- Headers HTTP : aucun `X-Robots-Tag`
- 404 propre sur les URLs inexistantes (donc tout le reste est crawlable)

Le `<link rel="canonical" href="https://villaplaisance.fr/">` aide, mais
Google peut l'ignorer si v2 reçoit des liens externes ou si le contenu
diverge de prod.

**Impact** : risque d'indexation duplicate, dilution autorité, message
"Duplicate, Google chose different canonical" en GSC.

**Cause racine code** : aucun mécanisme noindex preprod.
- `app/Views/layouts/front.php` : pas de `<meta name="robots">` du tout
- `app/Views/seo/robots.php:5-26` : sert toujours `Allow: /`, pas de
  conditionnel sur `APP_ENV`
- `.htaccess` racine : aucun `X-Robots-Tag`

**Fix code** :

1. `app/Views/layouts/front.php`, après le canonical (ligne 38) :
   ```php
   <?php if (APP_ENV !== 'production'): ?>
   <meta name="robots" content="noindex, nofollow">
   <?php endif; ?>
   ```

2. `app/Views/seo/robots.php`, conditionner :
   ```php
   <?php if (APP_ENV !== 'production'): ?>
   User-agent: *
   Disallow: /
   <?php else: ?>
   User-agent: *
   Allow: /
   ... (le reste du robots actuel)
   <?php endif; ?>
   ```

3. Bonus : sur o2switch, dans le `.htaccess` racine du subdomain v2 :
   ```apache
   Header set X-Robots-Tag "noindex, nofollow"
   ```
   Et idéalement Basic Auth (htpasswd) — c'est ce que prévoit le
   `CLAUDE.md` du projet ("Pendant les travaux : htpasswd sur le
   sous-domaine") mais pas encore appliqué.

### C2. JSON-LD `AggregateRating` invalide + téléphone placeholder

**Symptôme live** :
```json
"aggregateRating": {
  "ratingValue": "5.9",
  "reviewCount": 34,
  "bestRating": "5"
}
```

`ratingValue > bestRating` → Schema.org rejette le rich snippet et marque
le domaine comme suspect.

`telephone: "+33 6 00 00 00 00"` → numéro placeholder publié sur internet.
Signal de méfiance + Local SEO pollué.

`geo` : 18 décimales sur lat/long, signal "généré".

**Cause racine code** :
- `app/Services/SeoService.php:81` — `'telephone' => '+33 6 00 00 00 00'`
  codé en dur (pas branché sur `.env`).
- `app/Services/SeoService.php:200-208` — `aggregateRatingJsonLd()` fait
  `number_format($rating, 1)` **sans clamp**.
- `app/Controllers/Front/HomeController.php:41` :
  ```php
  $avgRating = array_sum(array_column($reviews, 'rating')) / count($reviews);
  ```
  Si la table `vp_reviews` contient des ratings sur une autre échelle
  (ex: /10), on génère `5.9/5`. Cause profonde : un seed avec rating > 5.
- `app/Services/SeoService.php:93-95` — la lat/long affichée en live à
  18 décimales vient du JSON-LD côté serveur, mais le code source les a
  déjà à 4 décimales (`44.0386, 4.8972`). À vérifier : peut-être que la
  prod sérialise un float plus précis. Cosmétique.

**Fix code** :

1. `SeoService.php:81` :
   ```php
   'telephone' => $_ENV['CONTACT_PHONE'] ?? '',
   ```
   Et virer la clé si vide (ne pas publier un champ vide). Ajouter
   `CONTACT_PHONE=+33...` dans `.env` et `.env.example`.

2. `SeoService.php:200-208` (clamp + worstRating) :
   ```php
   public static function aggregateRatingJsonLd(float $rating, int $count): array
   {
       $clamped = max(1.0, min($rating, 5.0));
       return [
           '@type' => 'AggregateRating',
           'ratingValue' => number_format($clamped, 1),
           'reviewCount' => $count,
           'bestRating' => '5',
           'worstRating' => '1',
       ];
   }
   ```

3. **Auditer le seed `vp_reviews`** dans `seeds/` : confirmer que les
   `rating` sont bien sur /5. Sinon, normaliser à la source.

### C3. Multilingue cassé

**Symptôme live** :

| URL | `<html lang>` | Title | État |
|-----|---------------|-------|------|
| `/`    | `fr` | FR | OK |
| `/en/` | `en` | **identique au FR** | Boilerplate seul traduit |
| `/es/` | `es` | **identique au FR** | Boilerplate seul traduit |
| `/de/` | **`fr`** | FR | **Page DE sert le contenu FR** |

Problèmes additionnels en live :
- **Aucun `<link rel="alternate" hreflang="...">`** sur aucune des 4
  URLs (vérifié `/`, `/en/`, `/es/`, `/de/`)
- **Aucun `x-default`**
- **Sitemap ne référence aucune locale** → locales orphelines
- **Aucune `<xhtml:link>`** dans le sitemap

**Causes racines code** (4 bugs distincts qui s'empilent) :

**a) `app/Lang/slugs.php` mappé à l'envers** (bug invisible en live mais
structurel) :
```php
'en' => [
    'bed-and-breakfast' => 'chambres-d-hotes',  // KEY = slug EN, VALUE = slug FR
    ...
]
```
Or `LangService::url('chambres-d-hotes', 'en')` (LangService.php:51) fait :
```php
$slug = self::$slugMap[$lang][$page] ?? $page;
```
Cherche `$slugMap['en']['chambres-d-hotes']` → introuvable (la clé EN c'est
`'bed-and-breakfast'`) → fallback `$page` → produit `/en/chambres-d-hotes`
au lieu de `/en/bed-and-breakfast`. **Le slugMap EN/ES n'a aucun effet
runtime.**

**b) `app/Views/layouts/front.php:36-38`** : le SeoService produit déjà
la liste hreflang correcte (`SeoService.php:49-60`, avec self + x-default),
mais le layout ne la rend pas. Il imprime canonical uniquement.

**c) `app/Views/layouts/front.php:101-106`** : sélecteur de langue avec
des liens `href="#"` (jamais résolus), affichant DE alors que
`SUPPORTED_LANGS = ['fr', 'en', 'es']` (config.php:22).

**d) DE pas dans `SUPPORTED_LANGS`** + `LangService::init()` fallback
silencieux sur DEFAULT_LANG → `/de/` sert le FR sans 404.

**Impact** : politique Google "scaled content abuse" potentiellement
applicable. Peut suppress rankings site-wide si DE/EN/ES sont vus comme
auto-translated / thin.

**Fix décisionnel** :

- **Option A (recommandée court terme)** : couper `/en/`, `/es/`, `/de/`
  (404 ou 301 vers `/`) jusqu'à avoir du vrai contenu traduit.
  - Retirer EN/ES/DE du sélecteur de langue (ne garder que FR)
  - Ne pas générer hreflang
  - Ne pas générer URLs `/en/` `/es/` dans sitemap

- **Option B (si on garde le multilingue)** :
  1. **Inverser `slugs.php`** (clé = slug FR canonique, valeur = slug
     localisé) :
     ```php
     'en' => [
         'accueil' => '/',
         'chambres-d-hotes' => 'bed-and-breakfast',
         'location-villa-provence' => 'villa-rental-provence',
         'espaces-exterieurs' => 'outdoor-spaces',
         ...
     ]
     ```
     Vérifier ensuite `app/Router.php` pour le décodage inverse
     (URL entrante localisée → page key canonique).
  2. **Ajouter la boucle hreflang** dans `front.php` après le canonical :
     ```php
     <?php foreach (($seo['hreflang'] ?? []) as $hl): ?>
     <link rel="alternate" hreflang="<?= htmlspecialchars($hl['lang']) ?>" href="<?= htmlspecialchars($hl['url']) ?>">
     <?php endforeach; ?>
     ```
  3. **Implémenter le sélecteur de langue** dans `front.php:101-106`
     avec `LangService::switchLangUrl(...)`. Retirer DE.
  4. **Traduire intégralement** `app/Lang/en.php` et `es.php` :
     title, meta description, contenu visible (pas seulement nav).
  5. **Régénérer le sitemap** avec `<xhtml:link>` (cf. C6 plus bas).

### C4. `Cache-Control: no-store` sur HTML public

**Symptôme live** :
```
cache-control: no-store, no-cache, must-revalidate
expires: Thu, 19 Nov 1981 08:52:00 GMT
set-cookie: PHPSESSID=...; path=/; secure; HttpOnly; SameSite=Lax
set-cookie: vp_vid=...; path=/; ...
```

**Impact** :
- Aucun edge cache possible (CDN, navigateur)
- Lighthouse perf cassée
- INP/LCP dégradés sur visites répétées
- Signaux Core Web Vitals négatifs

**Cause racine code** : `config.php:48-57` lance `session_start()`
**inconditionnellement** :
```php
if (session_status() === PHP_SESSION_NONE) {
    session_set_cookie_params([...]);
    session_start();
}
```
Or `config.php` est requis par `public/index.php` → tous les
contrôleurs front démarrent une session, même pour des pages publiques
(home, journal, etc.). PHP émet alors automatiquement
`Cache-Control: no-store`.

**Fix code** :
1. **Sortir** `session_start()` de `config.php` (garder uniquement
   `session_set_cookie_params()` ou la bloquer dans une fonction).
2. Créer une méthode `BaseController::startSession()` à n'appeler
   **que** dans :
   - `Admin/*Controller.php` (auth nécessaire)
   - `ContactController.php` (CSRF)
   - tout endpoint POST avec form
3. Sur les contrôleurs publics (Home, Chambres, Villa, Exterieurs,
   Journal, SurPlace, Hote, Itinerary, Legal), ajouter en tête de méthode :
   ```php
   header('Cache-Control: public, max-age=300, s-maxage=3600');
   ```
4. Vérifier que la bannière cookie (`front.php:154-194`) ne dépend
   pas du `$_COOKIE['vp_consent']` côté PHP (elle peut être full-JS).

### C5. URLs `v2.villaplaisance.fr` qui fuient dans OG / JSON-LD

**Symptôme live** :
```html
<meta property="og:image" content="https://v2.villaplaisance.fr/assets/img/og-default.webp">
<meta name="twitter:image" content="https://v2.villaplaisance.fr/assets/img/og-default.webp">
<script type="application/ld+json">{ "url": "https://v2.villaplaisance.fr", ... }
```

Si la prod est canonical, ces refs trahissent v2 et peuvent re-faire
découvrir le subdomain (et le rendre indexable s'il n'est pas noindex).

**Cause racine code** : 3 endroits utilisent `APP_URL` au lieu d'une base
prod-only.
- `SeoService.php:30` — `'image' => $seo['og_image'] ?? APP_URL . '/assets/img/og-default.webp'`
- `SeoService.php:80` — `'url' => APP_URL`
- `SeoService.php:96` — `'image' => APP_URL . '/assets/img/og-default.webp'`

Le canonical (ligne 42) est correctement basculé prod en preprod, mais
ces 3 lignes ne le sont pas.

**Fix code** — extraire le pattern dans une méthode interne :
```php
private static function publicBase(): string
{
    return APP_ENV === 'production' ? 'https://villaplaisance.fr' : APP_URL;
}
```
Et remplacer toutes les occurrences `APP_URL` SEO-publiques (og:image,
JSON-LD url/image) par `self::publicBase()`.

### C6. Sitemap mono-langue + trailing slash incohérent

**Symptôme live** :
- Sitemap : `<loc>https://villaplaisance.fr/chambres-d-hotes/</loc>` (avec `/`)
- Page : `<link rel="canonical" href="https://villaplaisance.fr/chambres-d-hotes">` (sans `/`)
- Les deux URLs servent en 200 sans 301 entre elles → duplicate URL.
- Aucune locale dans le sitemap.

**Cause racine code** :
- `app/Views/seo/sitemap.php:5-15` : URLs en dur avec `/` final, pas
  d'appel à `LangService::url()` ni à `SeoService::hreflang()`.
- `app/Services/LangService.php:48-57` : `url()` ne rajoute jamais le
  `/` final.
- → conflit canonical (sans slash) vs sitemap (avec slash).

**Fix code** :
1. Choisir une convention (avec slash recommandé pour pages section).
2. `LangService::url()` : rajouter le `/` final pour les pages != `/`.
3. `app/Views/seo/sitemap.php` :
   - Ajouter `xmlns:xhtml="http://www.w3.org/1999/xhtml"` sur `<urlset>`.
   - Pour chaque page, boucler sur `SUPPORTED_LANGS` + ajouter
     `<xhtml:link rel="alternate" hreflang="..." href="...">` pour
     toutes les locales (réciproques) + `x-default`.
   - Utiliser `SeoService::hreflang($pageKey)` pour cohérence.
4. Dans `.htaccess` racine v2/prod : 301 trailing slash :
   ```apache
   RewriteCond %{REQUEST_URI} !(/$|\.[a-z]+$)
   RewriteRule ^(.*)$ /$1/ [R=301,L]
   ```

## 🟠 Important

### I1. Headers de sécurité absents

**Symptôme live** : aucun `Strict-Transport-Security`,
`X-Content-Type-Options`, `Referrer-Policy`, `Content-Security-Policy`.

**Cause racine code** : `.htaccess` racine ne pose aucun header de
sécurité.

**Fix** dans `.htaccess` (à la racine du repo, ou `public/.htaccess`) :
```apache
Header set Strict-Transport-Security "max-age=31536000; includeSubDomains"
Header set X-Content-Type-Options "nosniff"
Header set Referrer-Policy "strict-origin-when-cross-origin"
```

---

### I2. `lastmod` du sitemap = `date('Y-m-d')` sur les pages statiques

**Symptôme live** : `<lastmod>2026-05-05</lastmod>` uniforme sur toutes
les pages → signal "tout est à jour aujourd'hui" = fake fresh.

**Cause racine code** : `app/Views/seo/sitemap.php:28` :
```php
<lastmod><?= date('Y-m-d') ?></lastmod>
```

**Fix code** : utiliser le `filemtime()` du Controller ou de la vue
correspondante, ou stocker un `last_modified` en BDD pour les pages
statiques. Les articles (ligne 39) sont déjà OK (lastmod depuis BDD).

---

### I3. Robots.txt sur v2 référence le sitemap de prod

**Symptôme live** :
```
Sitemap: https://villaplaisance.fr/sitemap.xml
```
Cohérent uniquement si v2 est noindexé (cf. C1). Sinon contradictoire.

**Cause racine code** : `app/Views/seo/robots.php:26` utilise déjà
`$base` (prod si `APP_ENV === 'production'`) — c'est cohérent. Le
problème est que v2 n'est pas noindex (cf. C1).

**Fix** : couplé avec C1. Une fois la conditionnelle `APP_ENV` ajoutée
au robots, il sert `Disallow: /` sans sitemap en preprod.

---

### I4. Sélecteur de langue dans le HEADER affiche DE et liens cassés

**Symptôme live + code** : `app/Views/layouts/front.php:101-106` affiche
DE alors que `SUPPORTED_LANGS = ['fr', 'en', 'es']`. Tous les liens =
`href="#"`. Confusion utilisateur + crawl bot vers `/de/` qui sert FR.

Couvert par C3 fix (b) et (c).
